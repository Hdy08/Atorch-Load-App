## 检查结论

在本次可解析的 AC632N 固件内容中，**未发现可识别的厂家数字签名**。能够确认的是 CRC16 校验及 JL ENC / SFC 数据混淆；已识别目录中没有独立的签名文件，已解析有效载荷之后均为 `FF` 填充。

后续已取得官方 BD19 ROM 字典并成功解压 BW150 / BW600 的启动程序，进一步定位了目录 CRC、芯片参数读取及 USB 分块接收 / 完成路径；具体地址、ROM 解码和 CRC 的 352 组纯内存指令模拟、CC 接收检查边界及尚未确认的实物 IAP / ROM 路径见 [启动程序与认证路径深入检查](firmware-boot-authentication-20261114.md)。原先“没有字典，无法还原启动程序”的限制已经解除。

本应用所称的“核准原厂文件”，实现上是已知参照文件的 SHA-256 白名单及本台设备升级实测，不是厂家公钥验签。文件来源可信、与参照内容一致、传输完整、适配硬件及正常启动是不同的判断，不能互相替代。

## 解析方法与 CRC 核对

使用本地已有的 `kagaimiq/jl-misctools` 新固件解析器中的文件条目、JLFS 迭代器和解码函数，在内存中处理原文件副本。解析器输出路径由内存对象替代，文件写出方法仅保存内存字节，不执行原解包命令的落盘流程。分析进程禁用 Python 字节码写入。

核对步骤为：

1. 读取原文件 / ZIP 条目，计算 SHA-256 并按内容去重。
2. 正确解码 Flash 头、顶层目录和应用区域，验证各级条目头 CRC。
3. 对实际包含的非预留文件及应用目录数据复算 CRC16，与条目中的值比较。
4. 从配置中解码 chipkey，再解析应用文件和资源。
5. 检查原始包、提取内容、有效载荷末端及标准签名特征；对 BW150 / BW600 的 DER 候选尝试 X.509 解析。
6. 核对压缩启动程序的 BANKCB 头、数据 CRC、LZ4 头和数据流中的字典引用。

这里的文件内部 CRC16 使用多项式 `0x1021`、初值 `0x0000`、不反射。它与 USB 升级帧的 CRC16/Modbus（多项式 `0xA001`、初值 `0xFFFF`）是两层不同校验，不能混用。

13 份 AC632N 文件的 Flash 头 CRC 均为 `3123`，正确解码后复算一致。全部已解析目录头和非预留数据 CRC 通过；预留区没有随包携带完整数据或使用 `FFFF` 占位时，不据此报告 CRC 失败，也不声称已验证对应设备 Flash 内容。

BW150 V1.1.0 的主要核对值如下。偏移为文件内位置，CRC 针对正确解码后的相应内容。

| 内容             | 文件偏移   | 数据字节数 | CRC16  |
| ---------------- | ---------- | ---------: | ------ |
| `uboot.boot`     | `0x0000A0` |     15,612 | `06CD` |
| `isd_config.ini` | `0x003D9C` |        122 | `6F83` |
| `app.bin`        | `0x004120` |    618,264 | `26BD` |
| `cfg_tool.bin`   | `0x09B038` |        718 | `C22A` |
| `p11_code.bin`   | `0x09B326` |      4,096 | `AE73` |

此外，BW150 应用区域目录的数据 CRC 为 `C640`；配置前 32 字节的 chipkey 编码数据，其内部 CRC 为 `336D`，均复算一致。本轮重新提取的五个文件与既有 `artifacts/vendor-bw150-firmware/` 中的对应文件逐字节一致；其中 APP 的 SHA-256 为 `afe464c4f358787bcaca409223e9c327926845b89e1f2d6dc3ada3181dab87cf`。

## chipkey 与 key_mac

### chipkey 是解码参数

全部 13 份 AC632N 文件均从 `isd_config.ini` 解码出同一个 16 位参数：`0x8D07`，十进制为 `36103`。JL ENC 使用该参数生成逐字节异或数据流，SFC 区域还结合块地址调整参数。

这是从包内可还原的混淆 / 解码参数，不是本次发现的数字签名，也没有构成公钥 / 私钥验签过程。不同文件使用同一 chipkey，不能据此鉴定某份文件由哪个发布者制作。

后续启动代码分析发现设备侧还会读取芯片控制器取得低 16 位参数；这可能形成与芯片配置有关的解码约束。包内取得 `8D07` 与实物 OTP / eFuse 读取是两种证据，本轮没有执行后者，详见深入检查报告。

### key_mac 条目指向包外区域

BW150、BW600 的顶层目录均包含：

| 属性              | 值                                 |
| ----------------- | ---------------------------------- |
| 名称              | `key_mac`                          |
| 目录头位置        | `0x80`                             |
| 描述的 Flash 地址 | `0xFF000`                          |
| 描述的长度        | `0x1000`，即 4,096 字节            |
| 属性              | `0x12`，由当前解析器作为预留区处理 |
| 数据 CRC 字段     | `FFFF`                             |

当前两份升级包的长度都未覆盖 `0xFF000`，没有包含该区实际字节。因此只确认存在这项区域描述，不能确认设备上该区存放什么，也不能凭 `key_mac` 名称认定它包含数字签名或消息认证码。

## 压缩启动程序：已解除的字典限制

BW150、BW600 的 `uboot.boot` 都是带一个 BANKCB 数据块的压缩启动程序。其 BANKCB 头和数据 CRC 均通过；LZ4 头指定相同的外部字典地址及长度。

| 项目                               | BW150 V1.1.0 | BW600 V2.0.5 |
| ---------------------------------- | ------------ | ------------ |
| BANKCB 加载地址                    | `0x2000`     | `0x2000`     |
| 压缩块字节数，包含 16 字节 LZ4 头  | 15,596       | 15,479       |
| LZ4 数据流字节数                   | 15,580       | 15,463       |
| 外部字典地址                       | `0x100000`   | `0x100000`   |
| 外部字典长度                       | 28,672 字节  | 28,672 字节  |
| 临时加载地址                       | `0xA000`     | `0xA000`     |
| 预期解压长度                       | 20,896 字节  | 20,832 字节  |
| 数据流中直接引用外部字典的匹配次数 | 375          | 374          |

最初解析 LZ4 token 后，确认数据流确实引用外部字典；直接不带字典解压失败。后续从杰理官方 BD19 Bootloader 仓库取得了 28,672 字节的参考 `rom.image`，并与另一官方 SDK 的 `rom.lst` 逐字节交叉核对一致。使用该字典已成功解压出 BW150 的 20,896 字节和 BW600 的 20,832 字节启动程序，长度均与头部一致。

解压后的代码已经可以检查，旧有字典障碍不再适用；但实物 ROM 修订、OTP / eFuse、独立 IAP 与设备预留区仍未读取，未识别到验签不等于排除全部认证路径。ROM 来源、提交、SHA-256、解压结果摘要、已确认的校验分支和复核示例见 [启动程序与认证路径深入检查](firmware-boot-authentication-20261114.md)。

## 与官方程序及本应用的关系

既有跨型号抓包证明官方程序允许把不适配当前硬件的其他型号固件完整发送出去，且可收到完成应答；这些结果不能证明固件适配或应用正常启动。另一方面，这些实验使用的是已有的不同型号文件，没有通过修改签名或认证字段来验证拒绝行为，不能据此证明官方程序或设备不存在数字签名检查。

本应用实机升级入口仍以固定的 BW150 V1.1.0 SHA-256 及已核准 USB 接口为限制。CRC 正确、能够解码、文件名型号相同或发现相同 chipkey，都不会扩大支持范围。本轮文档检查不改变文件接受条件和升级行为。

确认厂家数字签名还需要识别具体签名数据、覆盖范围和算法，并使用可信厂家公钥验证；确认设备会不会拒绝未经授权的固件，还需要设备侧认证路径证据。本报告只记录现有文件能够支持的结论。
