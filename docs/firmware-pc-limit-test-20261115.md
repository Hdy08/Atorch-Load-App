## 已定位的执行范围冲突

通过原厂 APP 中的实际指令和杰理固定版本 SDK 的寄存器定义，可核对以下设置：

| 对象             | 寄存器 / 指令位置           | 原厂与旧 B 的值             |
| ---------------- | --------------------------- | --------------------------- |
| CPU 配置         | `EMU_CON`，`0x001BE200`     | `0x80000017`                |
| Flash PC 下限    | `LIM_PC0_L`，`0x001BE21C`   | `0x01E00120`                |
| Flash PC 上限    | `LIM_PC0_H`，`0x001BE218`   | `0x01E9409C`                |
| RAM PC 下 / 上限 | `0x001BE224` / `0x001BE220` | `0x00007B60` / `0x0000A0A8` |
| ROM PC 下 / 上限 | `0x001BE22C` / `0x001BE228` | `0x00100000` / `0x00110000` |
| B 新增 MOV       | `0x01E97038`，6 字节        | 超出 Flash PC 上限          |
| B 返回 GOTO      | `0x01E9703E`，4 字节        | 超出 Flash PC 上限          |

APP 中该段初始化为：

```text
01E3F3CC  C0 FF 17 00 00 80    mov r0, #0x80000017
01E3F3D2  C1 FF C0 E1 1B 00    mov r1, #0x001BE1C0
01E3F3D8  08 43                sw r0, [r1 + 0x40]   ; EMU_CON
...
01E3F3F6  C0 FF 20 01 E0 01    mov r0, #0x01E00120
01E3F3FC  78 43                sw r0, [r1 + 0x5C]   ; LIM_PC0_L
01E3F3FE  C0 FF 9C 40 E9 01    mov r0, #0x01E9409C
01E3F404  68 43                sw r0, [r1 + 0x58]   ; LIM_PC0_H
```

`0x01E3F534` 的原指令 `49 17` 调用该设置函数入口 `0x01E3F3C8`；其所在初始化函数入口为 `0x01E3F44A`，由 `0x01E51432` 调用。这里只核对实际字节、调用位置和所选寄存器写入，不宣称完整仿真了启动过程。

A 通过原有立即数 MOV 把新文字地址交给原绘制流程，数据读取不要求 CPU 从新地址取指。B 则直接跳到原上限之外执行，这解释了为什么 A 的成功不能替代 B 的执行验收。新增代码起点高于原上限 `0x2F9C`，即 12,188 字节。

上一轮模型只检查钩子、分支和选定寄存器，没有把 CPU 已配置的 PC 范围纳入判断。这是此前离线验证的遗漏；原有模型检查通过的记录保留，不能据此覆盖 B 的失败反馈。

## 排查了跳转编码与代码搬移

本轮从杰理官方 SDK 固定提交 `fdc018de81629e21e594d677cf05f87d288be0f0` 读取 `cpu/bd19/tools/rom.lst`，用其实际指令字节和明确标注的目标地址，交叉核对 159 条直接 GOTO、368 条直接 CALL，共 527 条，目标零不一致。GOTO 重新编码也与原字节相同。该检查比“自编编码器与自编解码器互相一致”增加了独立的官方字节 / 目标依据。

这未发现旧 B 的分支编码或 PC 基准存在差 4 字节的问题；仍不把官方 ROM 样本当作新代码已在设备执行的证据。旧 B 的钩子目标、返回目标均保持原设计：`0x01E36ACA → 0x01E97038 → 0x01E36AD0`。

原启动代码中能看到从 `0x01E9409C` 复制初始化数据至 RAM `0x840`，以及从 `0x01E94E3C` 复制 RAM 段至 `0x7B60`。关于页钩子 `0x01E36ACA` 不在这两段 Flash 源范围内，没有据此将其当作搬移后的 RAM 代码。当前具体发现是 PC 范围冲突，实际复位原因仍待对照验证。

## B5 的唯一实验变量

新包文件为 `BW150-V1.1.0-JUMP4-LIMIT5-EXPERIMENTAL.bin`。以失败的旧 B 为基线，仅修改原有上限加载指令：

```text
位置：APP 映射 0x01E3F3FE；升级包偏移 0x433FE
旧 B：C0 FF 9C 40 E9 01    mov r0, #0x01E9409C
新 B5：C0 FF 48 70 E9 01    mov r0, #0x01E97048
```

新上限位于两条新增指令和 6 字节尾部填充之后。相对旧 B，APP 只有两个立即数字节变化，升级包共 10 字节变化：2 字节参数和 8 字节相关目录 / 载荷 CRC。钩子、新增短代码、`JUMP4` 文字、包总长、资源布局及其他文件内容逐字节相同。

`EMU_CON`、Flash 下限、RAM / ROM 范围及其他所选配置写入保持原值。该改动扩展 Flash PC 区间 12,204 字节，同时包含新代码之前原有的数据区；它不是仅赋予新增 32 字节执行范围，也不是关闭整个执行范围配置。

预期关于页型号仍显示 `BW150`，版本显示 **`JUMP4`**，USB 产品名仍为 `ATORCH BW150 V1.1.0`。保留与旧 B 相同的显示标记，是为了只测试上限参数这一变量。

## 本轮离线核验

- 原厂、旧 B、新 B5 的设置前缀，分别用选定编码模型和 SLEIGH P-code 核对 8 项写入；两套模型一致，B5 只改变 Flash PC 上限。
- 新增保守区间检查要求每条选定指令的完整字节区间落在配置范围内。旧 B 的两条新增指令检出越界；B5 全部包含。另将上限故意设在新增 MOV 之后、返回 GOTO 之前，检查按预期检出不完整覆盖；负例只在内存中运行。
- 原厂与 B5 的两条显示分支、8 种初始状态，共 32 组、160 条选定指令步骤；B5 的 256 组钩子状态、768 条步骤均回到 `0x01E36AD0`，所选模型中只有 `r8` 改为文字地址。
- 10 项结构 / CRC 损坏负例均由离线解析器按预期拒绝，包括恢复旧上限但不更新 APP CRC 的负例。没有把损坏固件交给设备。
- B5 经既有第三方解析器核对，五个成员和完整解码容器一致；两种构建路径输出相同包。撤销上限修改可逐字节回到旧 B，缩回原 APP 可逐字节回到原厂。
- 新增布局沿用 A / B 的 32 字节扩展；旧四轮清单覆盖的 30 个文件及其清单均复核保持原样。原厂输入文件、前轮脚本及冻结产物没有改写。

以上是包结构、官方编码参照、有限状态和配置范围检查，不是 CPU 异常系统、缓存、完整 UI 或整机仿真。PC 上限寄存器的实际运行值、复位异常位及取指现场尚未从设备读取。随后 B5 获用户验收通过反馈，支持这一修正与现象的因果解释；仍未捕获具体异常位或复位现场。
