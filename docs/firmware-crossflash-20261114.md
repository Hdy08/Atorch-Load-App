## 完整传输的核对结果

主句柄 `0x85ac668` 的协议计数如下，另一句柄的重复应答单独排除：

| 发送 | AA   |     1 | 块数和尾块大小匹配                  |
| 接收 | BB   |     1 | 就绪参数匹配                        |
| 发送 | CC   | 5,591 | 索引连续，无缺块，无重复发送        |
| 接收 | DD   | 5,590 | 对应索引及可见回显匹配              |

| 接收 | `11` |     0 | 未见协议拒绝帧                      |

另一个官方句柄 `0x85aa638` 收到 85 条重复应答（83 DD、1 EE、1 FF），不计入主传输。索引 90、3678、4459 处出现读回调先于对应写 API 返回被记录；应答均在写调用开始之后，且下一块写入均在上一块应答之后。两个方向各自的索引连续，不能将这些跨线程 API 完成回调的记录顺序当作物理 USB 包乱序。

## FF 之后与恢复情况

冻结抓包中 FF 之后的正常 APP 回复为 0；官方程序继续在旧句柄上发送普通查询，写入返回 `-1` 共 214 次，后续针对 `0483:5750` 的打开请求未成功。另用只读 HID 枚举工具检查时，没有发现 `0483:5750` 接口；旧句柄写入失败本身不能代替枚举结果，也不能证明 WIFI 传输是否工作。

用户在此时确认：“**未进行任何操作，显示升级中，Upgrade Channel: WIFI**”。这项屏幕现象来自用户反馈，本轮没有工具截图；该观察发生在用户进一步断电、按键或刷回之前。

抓包停止、原始记录冻结后，用户反馈“**已恢复**”。本轮没有独立记录恢复过程，也未再次进行恢复后的 USB 参数、标定值或遥测回读，不将此前 BW150 验收的参数保持结果移用到本次恢复。

## 可确认的结论与未确认事项

本轮可确认：官方主机完整发送了未经改写的 DL24EW-573 文件，可见 IAP 协议未返回拒绝，并报告 EE / 零状态 FF；随后没有恢复正常应用通信，用户看到 WIFI 升级页面。因此，**完整传输和 FF 完成应答不能单独证明固件适配硬件或应用可启动**。

本应用的 AC632N 文件检查和 BW150 V1.1.0 精确 SHA-256 限制保持不变。本轮使用官方程序的实验不代表本应用已开放 BW600 或 DL24EW 实机升级。

### 分析结论与证据归档

本轮支持“BW600 的应用硬件配置或解释方式与本台 DL24 不完全匹配”这一判断：整文件传输正确，USB 应用已运行，但显示和遥测字段异常；恢复 BW150 后显示与读数恢复。这仍是基于现象的推断，不能直接定位到 LCD 驱动、ADC 引脚、传感器曲线或某一标定表。DL24EW 阶段没有正常 APP 回复、BW600 阶段有正常格式回复，是两种不同的失败表现。

IAP 在此次跨型号切换后仍枚举为 BW150 V1.0.2 并能够重新传输已核准 BW150 文件，说明本轮恢复路径可用；没有证明启动区二进制完全未变或具有写保护。不能将该结果推广为任意错误固件可恢复，也不扩大本应用的实机升级白名单。
