`XXXX` 是本次上电以来的快照计数低 16 位，以十六进制显示；每满 `FFFF` 回到 `0000`。USB 回复保留完整 32 位计数。进入关于页不会触发计数；离开关于页、断开 USB 或仅使用蓝牙时，原厂数据任务仍负责执行。真正断电后计数和新增统计归零。

快照周期为 **100 个 OS tick**。本包不把参考 SDK 的 tick 频率直接当作这台设备的实测值；只读工具会对照主机时间给出实际 tick/s 和 snapshot/s。观察计数应持续增加，不要求用户反馈恰好每秒加一。

异常状态在版本位置显示 `1:ERR!` / `2:ERR!` / `3:ERR!`。对应诊断标志位：`01` 为 ROM 来源字节未匹配，`02` 为预留 RAM 边界标记异常，`04` 为采样出现 NaN / Infinity，`08` 为第 3 包选定快照校验异常。`80000000` 只用于 USB 读到并发更新时的临时 busy 回复，主机工具会重试。出现稳定的 `ERR!` 应先保留现象和日志，本轮不能按通过记录。

## 第 1 轮：周期运行与真实数据

1. 用此前已成功的官方升级流程刷入 RT1，完成后打开设备关于页，确认版本位置为 `1:XXXX`。
2. 记下计数，返回正常监测页，等约 10 秒再进入关于页，计数应继续增加；重复两次。这样验证独立周期路径，而不是反复进入页面时才执行代码。
3. 在原来已正常使用的输入条件下，与设备正常显示 / 原厂 USB 遥测对照电压、电流、功率和可用温度。温度各字段分别对应 MOS、探头、CPU；不把 MOS 温度另计为“设备温度”。至少保持一段稳定输入，供脚本对照。
4. 检查显示刷新、常用按键、USB 监测正常，没有非预期复位或负载启停。
5. 完全断电后冷启动一次，确认能正常进入应用、计数从新会话开始并继续增加。重新启动不是“复用上一会话统计”。

只读诊断可运行交付目录的 `1-verify-runtime.ps1`，默认记录 60 秒。也可在 PowerShell 直接运行：

```powershell
& 'C:\Users\Administrator\AppData\Local\Python\bin\python.exe' -B 'D:\Documents\Code\Atorch-Load-App\tools\verify_firmware_runtime.py' --stage 1 --seconds 60
```

运行前关闭占用 USB 的官方程序和重构应用。脚本只发 `03` / `05` / 带固定令牌的 `52` 读请求，不刷写、不启停负载、不更改参数。记录输出到单独的新目录 `artifacts/firmware-runtime-RT1-hardware-时间`，控制台显示路径。

**通过标准：** 关于页关闭时计数仍前进；稳定条件下真实数据符号、单位和数值一致；未出现 `ERR!`、非预期复位或常用功能异常；冷启动后仍可运行。脚本只完成诊断窗口的观测，电气精度及显示 / 按键验收仍要结合实际现象。

## 第 2 轮：实际监测功能与接口

1. 刷入 RT2，确认 `2:XXXX`，先做第 1 轮的页面退出和基础读数检查。
2. 在既有正常测试范围内产生至少两档输入 / 电流变化，再回到初始条件。USB 极值页应包含采样确实观察到的电压、电流、MOS 温度范围；当前值回落后最大值不能随之回落，最小值同理。极值自上电开始统计，启动时实际采到的零值也会计入。
3. 正常启停负载至少 3 次，每个状态保持超过一次快照周期。诊断里的启停次数应随观测到的状态变化增加。比快照周期更短的动作可能合并，不能用此计数代替硬件边沿捕获。
4. USB 断开再连接，计数和极值应延续；若使用手机，检查既有 BLE 监测和面板遥控仍正常，再断开 BLE 回到 USB 验证。本轮未新增 BLE 私有诊断或宣称 BLE 新功能已通过。
5. 重复读诊断和返回页面；原有模式 / 目标值 / 显示设置操作仍应正常。需要检验原厂设置持久化时可沿用原来的亮度等设置进行冷启动对照；**新增快照和极值本身是易失数据，不保存至设备 Flash**。
6. 冷启动后确认新增极值 / 计数是新会话，并随新数据更新。

运行 `2-verify-monitor.ps1`，或：

```powershell
& 'C:\Users\Administrator\AppData\Local\Python\bin\python.exe' -B 'D:\Documents\Code\Atorch-Load-App\tools\verify_firmware_runtime.py' --stage 2 --seconds 180
```

工具会同时保存当前快照、极值和原厂遥测。每个私有回复采用有界重试以保证本条回复的状态一致；几个不同回复和原厂 `05` 不构成同时采样，变化期间的相邻读数差异会保留在日志中。自动输出 `diagnostic_window_passed_manual_acceptance_pending` 不表示这张清单的人工项目已通过。

**通过标准：** 极值覆盖已观察到的变化且会话内保持；启停状态长于快照周期时能被统计；USB / BLE 常用行为、重复操作和冷启动符合上述定义；无稳定错误标志或非预期复位。

## 离线证据与实现范围

- 生成器：`tools/firmware_runtime_suite.py`。三包都从固定原厂 SHA 构建，不叠加前包的已修改 APP。
- 真实路径：原厂 `cl24_data_task`，入口 `0x01E06ADE`，注册位置 `0x01E04906`；挂接其循环中的原有延时调用 `0x01E06B00`，保存 / 恢复新增逻辑用到的寄存器后进入原来的延时入口。
- RAM：将原厂物理页分配器结束参数从 `0xFB60` 改为 `0xFA80`，参考实现按 128 字节对齐后减少一页；明确预留 `0xFA80..0xFAFF`，不借用原厂变量空隙。上电初始化发生在 Flash PC 范围设置后、应用任务创建前。初始化时匹配实际 ROM 的 tick 读取和分配器边界指令，共 32 字节；不匹配则关闭新增数据读取并显示错误。
- 额外钩子栈深 36 字节；原有 USB 接收帧中的私有回复使用其已拥有的 64 字节报告缓冲区。模型逐条限制新增写入范围，没有向采样源、控制寄存器、参数 / 校准区或非易失存储写入。
- 新增 USB `52` 必须带固定 `RT` / 版本令牌；仅返回自有状态。原有命令范围仍走原厂分支，其余输入保留忽略行为。主机解析器自身只允许生成读命令。
- 原厂全文件前 `0x4000`、非 APP 成员、配置与 P11 内容保持；APP 扩展 3,200 字节，沿用已验证的资源移动方式，文件总长不变，剩余尾部 90 字节。反向重建与原厂逐字节相同。
- 实际使用手工汇编的已验证 q32s 指令及局部函数，没有采用新的 C 编译 / 链接产物，因此不将本轮结果写成通用 C ABI 已验证。
- `stage-1/2/3.analysis.json` 保存字段解码与 SLEIGH P-code 双模型结果、全部 256 个命令分发控制、ROM 逐字节不匹配、并发读取、非有限值、内存保护标记、计数回绕及校验故障等证据。故障注入只在电脑内存中，未输出故障固件。
- `stage-1/2/3.listing.txt`、源码快照、清单和只读工具随交付目录保存。历史 NUM8 等九轮证据清单及其文件重新核对，通过与否没有被新包结果覆盖。
