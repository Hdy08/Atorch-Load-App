# 固件真实性与启动认证：现有资料核查汇总（2026-11-15）

检查日期：2026-11-15，北京时间（UTC+8）。本文继续 [固件签名静态检查](firmware-signature-inspection-20261114.md) 和 [启动认证深入检查](firmware-boot-authentication-20261114.md)，将检查扩大到全部本地原始固件、嵌套资料包、三种包内启动程序、三份官方 PC 程序、两份 Android APK 的证书材料，以及固定版本的杰理官方参考 ROM / Bootloader SDK。

本轮只进行文件分析和电脑内存中的解析，没有连接设备、发送 USB / BLE 命令、运行官方升级程序或刷写固件。既有实机现象引用 [跨型号刷写记录](firmware-crossflash-20261114.md)，不是本轮新增实验。本轮只增加分析文档、复核脚本及证据摘要，不修改应用的升级保护和白名单。

## 结论及证据强度

**现有资料没有提供可核验的厂家固件数字签名。已查明的官方 PC 升级入口和包内启动 / HID 升级路径，使用的是文件大小、目录结构、CRC、芯片解码参数、传输序号及解压长度等检查。不能把这些检查、FF 完成应答或本应用的 SHA-256 白名单称为“厂家验签通过”。**

相较前一轮，增加了五项实质证据：

1. 全部 10 份不同内容的 AC632N 固件均成功解压启动程序，按完整解压内容去重后只有 **3 个家族**；其中 BW150 与这些 DL24 版本的包内启动程序逐字节相同。
2. 直接追踪了官方 BW600 PC V1.0.8 的选文件、开始传输和应答处理。选文件入口未解析厂家签名或型号；FF 分支直接进入界面完成处理。BW150 PC V1.0.5 的文件读取、大小限制和 AA 构造有相同结构。
3. 包内 HID 升级程序按已有 Flash 目录定位 app_dir_head，跳过输入文件在应用区之前的内容，并将应用区首个擦写块最后写入。**文件被整包传输不代表其中 uboot.boot 也被安装。**
4. 公开参考 ROM 从复位入口、用户态入口到 Run_App 正常加载路径已继续追踪：确认了 Flash 头 / BANKCB CRC、读取重试、LZ4 解压及长度比较，没有在这条已识别路径中发现厂家公钥验签步骤。
5. 两份官方 Android APK 中确实存在同一张 RSA 2048 位自签名证书；其证书自身签名已核对，但没有证据把它用于固件验签。该公钥及其正反字节序模数未匹配所检查的固件原文件、解码容器、提取文件和解压启动程序。

上述结论分别对应文件、特定程序路径和公开参考 ROM。**仍不能证明实物 ROM、当前驻留 IAP、OTP / eFuse 或自定义编码中绝无其他认证。** “未发现验签”与“数学上证明所有代码都不存在认证”是不同强度的判断。

本节 PC 地址均为 32 位 PE 的虚拟地址，ImageBase 为 0x400000；与包内 MCU 地址是两套地址空间。

### BW600 PC V1.0.8

程序文件：Load_Application.exe；大小 2,649,088 字节；SHA-256：

| 应答 | 静态检查结果                                                                                                                  |

## 包内 HID 升级如何写入 Flash

这一部分纠正“传输整个升级包，所以包内 Bootloader 一定被刷入”的推断。下面详细数据流以家族 A 为准；B / C 也分别核对了目录打开、CC 分支和最后写入 / FF 片段。

### 写入目标来自现有 Flash 目录

| A 家族地址    | 数据流                                                                      |
| ------------- | --------------------------------------------------------------------------- |
| 0x42AC–0x42C0 | 为全局对象 +0xA4 的文件描述结构打开 app_dir_head；字符串地址为 0x6E59       |
| 0x2B46–0x2C58 | 目录查找函数；目录头解码后核对 CRC 和文件名                                 |
| 0x2C38–0x2C4E | 将目录项的数据偏移、长度、初始位置 0、标志填入文件描述结构的 +0、+4、+8、+C |
| 0x4CA6–0x4CB0 | AA 握手时再次按同一名称打开目标文件                                         |
| 0x2E64–0x2E94 | 写入地址由文件基址 + 当前文件位置形成，交给 SPI Page Program 路径           |
| 0x2DA4–0x2E48 | 擦除同样以文件描述结构的基址 / 位置为起点，再推进位置                       |

**全局 +0xA4 保存的是文件描述结构的首字段，即目标文件基址，不能误标为“固件总长度”。** 本地全部 AC632N 包的顶层 app_dir_head 都指向 0x4000；uboot.boot、isd_config.ini 和顶层头位于其前方。

因此，对已识别的正常布局和这一 HID 升级路径，代码指向的是应用区更新；不是先从地址 0 覆盖整个 Flash。这里的目录来自正在运行的设备 Flash，不能只用待传文件的目录替代实机目录事实。

### 跳过输入前缀，最后补写应用区首块

令 A 为当前目标文件基址、B 为当前 Flash 配置取得的擦写块大小：

    skip_to = A + B
    boundary_block = floor(skip_to / 58)
    boundary_remainder = skip_to % 58

A 家族 0x4A46–0x4A5E 正在计算上述边界。CC 接收路径累计输入字节数：跳过 A 之前的前缀，把 [A, A+B) 暂存在 RAM；到达边界块后，将余下数据写入后续位置。

0x52EA–0x5330 处理最后剩余缓冲，再将文件位置设回 0，以暂存地址 0x79A0 和块大小 B 调用写入函数。**这是应用区首块后写，不是把整个镜像到最后一次性写入。** 本轮没有假设每颗实际 Flash 的 B 都是固定 4 KB。

| 关键操作                 | A：BW150 / DL24 | B：BW600        | C：CW           |
| ------------------------ | --------------- | --------------- | --------------- |
| 打开 app_dir_head 的调用 | 0x42C0 → 0x2B46 | 0x426E → 0x29DE | 0x4202 → 0x29DE |
| CC 提前跳入数据分支      | 0x4C66 → 0x50C6 | 0x4C2C → 0x5084 | 0x4BCE → 0x502E |
| AA CRC 调用              | 0x4C88 → 0x3530 | 0x4C4E → 0x3524 | 0x4BF0 → 0x3568 |
| 最后补写首块             | 0x5330 → 0x2E50 | 0x52EE → 0x2DFE | 0x5298 → 0x2E18 |
| 随后构造 FF              | 0x5348          | 0x5306          | 0x52B0          |

三个家族最后补写首块的调用返回后，都紧接着重新赋值 r0 并延时，随后构造 FF，没有在这个调用点依据写入函数返回值作成功 / 失败比较。未发现完成路径对整个已写应用区读取并比较摘要的步骤。不能因此否认底层 Flash 函数内部的忙状态检查，但 FF 本身并非完整写后校验结果。

A 家族完成后在 0x5386 调用 0x3622：清理 USB / 控制寄存器、写入启动标记，最终跳到 ROM chip_reset 入口 0x106F44。没有在这段重启前路径发现厂家公钥验签调用。

### 与既有实机观察的关系

上述静态路径能解释“BW600 应用已启动，但恢复时仍看到 BW150 IAP”以及“非 AC632N 文件得到 FF 后不能正常进入 APP”等现象的一部分机制。它**不是实机 Flash 回读**，也不证明错误文件具体执行到哪一条指令、哪个启动检查拒绝了它，或启动区具有不可写的硬件保护。

能够更肯定地说的是：**包内 uboot.boot 的分析与实机当前 IAP 的鉴定需要分开；后续整包传输成功不能自动填补二者逐字节一致的证据缺口。**

### 从复位到 BANKCB / LZ4

已经追踪 _start 0x100000 → startup 0x10500E → RTI 后 _user_mode 0x10505C → main 0x10605C。main 构造的 Flash 读取函数指针指向 norflash_read 0x10657C，并调用 Run_App 0x105E2C。

在这一正常 Flash 加载入口中，Run_App 的 r5 / r6 / r7 间接调用均从同一参数结构 +0xC 取得读取回调，不能仅因它们是间接调用就标为未知验签钩子；最终 call r8 则是移交给加载代码的边界。

| ROM 地址          | 已确认步骤                                                                             |
| ----------------- | -------------------------------------------------------------------------------------- |
| 0x105E3E–0x105E4E | 读取 32 字节 Flash 头；对后 30 字节计算 CRC，与保存值比较；CRC 为 0 也拒绝             |
| 0x105E60          | 读取第一个顶层目录项                                                                   |
| 0x105E66–0x105E8C | 最多四次尝试读取 BANKCB 头，检查 14 字节 CRC 及保存值                                  |
| 0x105EC2–0x105EE6 | 最多四次读取加载块，取硬件 CRC 结果 0x1E3504，核对 BANKCB 数据 CRC，拒绝不匹配或零结果 |
| 0x105EEC–0x105F18 | 压缩标志为 0x40 时设置外部字典，调用 LZ4_decompress_safe_continue，核对输出长度        |
| 0x105F1C–0x105F32 | 准备执行环境并 call r8，进入加载的启动程序                                             |

已识别的这条流程中没有“取得厂家可信公钥 → 散列固件 → 验证数字签名”的步骤。norflash_read 还会配置硬件解码 / CRC 控制寄存器，例如 0x1E4100；CPU 指令列表本身不足以说明所有硬件密钥、OTP 和芯片修订条件。因此不能将此结论扩展为“任何硬件条件下都能启动任意数据”。

### 密码服务、SDK 锁及其他入口

ROM 确实包含 SHA-256、HMAC、ECC 和 _sdk_mkey_lock。针对复位、用户态、main、Run_App 和 norflash_read 显式入口建立的**直接调用 / 尾跳边**图可达 61 个命名函数，未进入这些命名密码服务。这是辅助枚举，不是全 ROM 可达性或所有中断 / 间接调用的形式化证明。

_sdk_mkey_lock 0x106B88–0x106C0B 的原始指令已经读完：复制 32 字节数据、以其中的 16 位参数调用 doe、核对 26 字节 CRC、比较 0x53594B4A 常量，再把若干字段及硬件寄存器值异或进 0xFC0C 的全局量 puk。该函数没有 RSA / ECDSA 验签过程；也没有把一个可信厂家公钥与完整固件签名配对验证。名称含 lock 或变量名 puk 均不足以证明它是厂家固件签名验证器；它仍可能承担 SDK / 芯片参数绑定作用。

另外两类路径已作区分：

- boot_poweroff 在 0x105166 间接移交低功耗恢复入口，前面检查恢复标记与状态；不是正常固件文件验签入口。lp_signature_set 写的是恢复标记，signature 在此处不表示数字签名。
- ROM USB 下载器有运行期钩子和外部地址执行，例如 0x102F10、0x10305E；UART 下载器在 0x105824–0x10582A 比较接收载荷 CRC，可在 0x105850 解码，再于 0x105868 调用接收入口。这些入口最后可能执行外部加载程序。未提供的外部程序和实际下载会话不属于现有 ROM 字节能覆盖的内容。

没有尝试利用这些下载入口、构造解锁载荷、改写密钥或触发实机拒绝实验。

## 指令工具盲区的处理与保留

旧 q32s SLEIGH 对部分三操作数移位、栈操作和长条件跳转没有定义。本轮补充解码，并与官方 rom.lst 中的 **111 条对应编码实例**逐项比较寄存器、操作数、条件、跳转目标和栈寄存器集合，全部相符；脚本保留并列输出及这一检查。其中包括移位、栈操作和长立即数比较。

长分支目标按“指令地址 + 6 + 有符号位移 × 2”恢复。家族 A 的 0x3F04、0x3F12、0x3F18、0x5618 等此前难以解码的跳转已可继续追踪，涉及双 bank / 布局元数据检查。长寄存器比较与两个栈编码仍保留“由相关 ISA 定义推断”的标签，不能冒充都在参考 ROM 找到了相同实例。

| 家族 | 含内嵌数据的线性记录数 | 使用补充解码的记录数 | 仍标为 unknown 的记录          |
| ---- | ---------------------: | -------------------: | ------------------------------ |
| A    |                  5,342 |                   75 | 0x4DDA、0x4DDC、0x4DF6、0x57CE |
| B    |                  5,298 |                   75 | 0x4D96、0x4D98、0x4DB2、0x578A |
| C    |                  5,289 |                   75 | 0x4D42、0x4D44、0x4D5E、0x5736 |

这些 unknown 均位于已识别的 tbh / tbb 跳转表内，是表数据，不应继续视为缺失四条执行指令。线性扫描还会把其他跳转表数据错译为 call r0 / call r3 等；证据中保留了表范围和这种误判的标记。

已定位的真实间接调用主要是 USB 描述符 / 接口 / 端点回调与应用入口，例如 A:0x2F5C 的描述符回调、0x5720 等 USB 中断回调及 0x4636 的 APP 入口。多个回调可追到 0x203C、0x22C6、0x2388、0x238A、0x23F6 的固定注册位置；运行期状态及所有内存可能值没有经过形式化证明。

因此，“工具仍有若干无法识别的执行指令，所以不能分析”这一旧限制已明显收窄；**记录数不是执行覆盖率，未知记录都落在表内也不等于所有控制流已被形式化验证。** 复核脚本不修改本地反汇编器定义，也没有把补充解码器用作实际刷写依据。

## 剩余边界：资料缺失与证明方法缺口分开记录

本轮列出的库存、解压、标准容器搜索、已识别 PC 文件入口、包内启动 / 升级关键路径和参考 ROM 正常加载路径已经完成，没有将上述项目留为“稍后再检查”。

**必须补充新证据才能确认的事实：**

- 实物芯片完整 ROM 与公开参考 ROM 是否同一修订。解压字典匹配不等于已经读过芯片全部 ROM。
- 当前驻留 IAP 与哪一份包内启动程序逐字节相同。应用区更新会保留前缀，使这一边界更不能由“已刷同包”自动消除。
- 物理 OTP / eFuse 和 key_mac / 设备预留区的真实内容、访问限制及硬件解码状态。全部包都只声明 key_mac 在 0xFF000、大小 0x1000，该范围超出现有包长；占位项不是该区内容。
- 缺失的外部下载器、完整厂家安全启动说明、可信厂家公钥 / 证书链、明确签名值和覆盖范围。
- 哪项检查在实机上拒绝什么输入，以及错误数据是否真的写入何处。需要特定实验或 Flash 回读，现有 API 抓包无法补出这些内容。

**不能伪装成单纯资料缺失的证明方法边界：**

- 标准格式扫描不能证明不存在任意自定义编码的签名 / 密钥。
- 已读关键路径、直接调用图和补充反汇编，不等于全部中断、间接调用、内存状态和自定义算法的形式化覆盖。
- 将更多普通应用代码反编译，理论上仍可能发现新线索；但现有结果没有给出可继续配对验证的厂家签名、公钥或未解释的明确验签调用点。不能因为尚有其他应用功能可逆向，就声称它们会补足真实性证明。

因此，针对“这批固件是否包含可验证的厂家签名、官方工具如何检查、包内启动程序何时接受输入”这些问题，现有材料的可重现核查已经覆盖本报告清单；没有据此宣称绝对证明任何设备状态下都不存在认证。
