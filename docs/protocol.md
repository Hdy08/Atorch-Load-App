# BW150 USB 协议记录

证据来源：本地 `BW600_PC_Application_V1.0.8/Load_Application.exe` 的导出函数、Qt 元对象、收发解析函数，以及已连接 BW150 V1.1.0 的实际 HID 报文。原程序 SHA-256 为 `80BA4378F4C616E9E2B5C99FA893FF8E3CE03C7B3816A266618CE3D64C9BCC31`。

这里只标明已经找到的字段。其他 BW 系列型号尚未验证。

## USB 传输

- VID `0483`，PID `5750`，HID Usage Page `FF02` / Usage `02`。
- 输入、输出均为 **64 字节无编号 report**。
- Windows HIDAPI 写入需传入 **65 字节**：第一个字节为 `00`，之后是 64 字节设备协议报文。`55` 是协议头，不能当作 report ID。
- Android USB Host 直接读写 64 字节 interrupt endpoint，不加 Windows HIDAPI 的 `00` 前缀。
- 当前设备地址 `01`，所有多字节偏移均从协议报文第 0 字节开始。

设备描述符：`0602ff0902a1010903150026ff007508954081000904150026ff00750895409100c0`。

## 查询与回复

查询参数：`55 05 01 03 0B 00 8C EE FF`，余下补零至 64 字节。查询实时数据将第 3 字节换为 `05`。

参数回复以 `AA 05 01 03` 开头，以偏移 62 的 `EE FF` 结尾。普通模式偏移 4 起连续 11 个 **大端 IEEE754 float32**；特殊模式的首项可能为其他载荷，不统一当作浮点数：

| 偏移  | 字段                                                                            |
| ----- | ------------------------------------------------------------------------------- |
| 4     | CC / CV / CR / CP / CDC / CDCDC 的目标值；IR / POWER / CABLE / CDxn 暂为 `null` |
| 8     | 温度校准系数（无量纲，1.0000 为原比例）                                         |
| 12    | 电压校准系数                                                                    |
| 16    | 电流校准系数                                                                    |
| 20    | 截止电压 V                                                                      |
| 24    | 充电上限电压                                                                    |
| 28    | 充电截止电流                                                                    |
| 32    | 过流保护                                                                        |
| 36    | 过功率保护                                                                      |
| 40    | 探头温度上限                                                                    |
| 44    | MOS 温度上限                                                                    |
| 48–54 | 模式、语言、工作亮度、待机亮度、待机秒数、时限小时、时限分钟，各 1 字节         |

2026-11-13 更正：初版把偏移 8 的温度校准系数与偏移 20 的截止电压互换，造成上述帧被显示为截止 1 V、温度“补偿”约 2.5。用户对照面板确认截止 **2.50 V**、温度校准 **1.0000** 后，Windows 再次只读捕获到相同字段。原程序 `0x43ab82 / 0x43abdc` 分别将它们保存到参数结构 `+0x38 / +0x44`；`0x40838a` 用 `+0x38 × 1000` 设置温度校准滑块，而 `0x406ca8 → 0x4083df` 将 `+0x44` 显示到截止电压输入框。回复顺序按 `26 / 27 / 28 / 29` 命令排列，不能按页面控件顺序推断。历史快照保留原始错误字段名，不作为正确物理值的依据；本次没有写入校准或截止电压。

实时回复为 `AA 05 01 05`，偏移 8 起连续 10 个 **小端 uint32 / 1000**，依次为电压、电流、功率、**电阻 Ω（20）、电量 Wh（24）、容量 mAh（28）**、CPU 温度、探头温度、MOS 温度、风扇 RPM。

容量、电量、电阻的初版映射曾错位。用户对照设备指出后已更正，并在捕获帧测试中分别断言 `6599.362 mAh`、`129.664 Wh`、`0 Ω`。CSV 与界面直接使用这些已修正的统一字段。

## 写命令

普通控制帧为 `55 05 地址 命令 载荷[4] EE FF`，补零至 64 字节。float32 载荷为大端。

| 命令       | 含义                                   | 载荷                                                                    |
| ---------- | -------------------------------------- | ----------------------------------------------------------------------- |
| `21`       | 目标值                                 | float32                                                                 |
| `25`       | 启停负载                               | 第一个载荷字节 `00/01`                                                  |
| `26/27/28` | 温度 / 电压 / 电流校准系数             | float32                                                                 |
| `29/2A/2B` | 截止电压 / 充电上限电压 / 充电截止电流 | float32                                                                 |
| `2C/2D`    | 过流 / 过功率保护                      | float32                                                                 |
| `2E/2F`    | 探头 / MOS 温度上限                    | float32                                                                 |
| `22/23/24` | 工作亮度 / 待机亮度 / 待机秒数         | **最后一个**载荷字节                                                    |
| `31`       | 运行时限                               | 第一个载荷字节为数值，最后一个为 `01` 小时 / `02` 分钟                  |
| `32/33/34` | 电流归零 / 出厂设置 / 累计数据归零     | 全零载荷                                                                |
| `20`       | 原应用语言动作                         | 原程序有四个动作；读回语言值的语义尚未完全核实，暂不开放 UI             |
| `47–50`    | 进入测试模式                           | 4 字节全零；模式与命令映射见下表                                        |
| `35`       | CDC / CDCDC 提示操作                   | 第一载荷字节为 `1 / 2 / 3 / 5`，含义依赖当前提示；见 `special-tests.md` |

参数写入在实际 BW150 上主要返回新的 `03` 参数帧，不能只等待 `04` ACK。当前驱动写入一次，主动查询参数和实时状态，以对应字段回读一致或成功 ACK 作为确认；超时不自动重发写命令。测试已验证目标值原值写回和 STOP。其他参数的编码来自原程序静态分析，尚未逐项在硬件上写入验证；校准、累计清零、出厂设置均未对实机执行。

ACK 以 `AA 05 地址 04` 开头，偏移 4 为状态，偏移 8–9 为 `EE FF`。状态 `01` 为成功。

累计数据清零沿用原程序 `on_settings_btn_datazero_clicked`（`0x40da40`）发送的 `55 05 地址 34 00 00 00 00 EE FF`。BW150 V1.1.0 的 `34` 分支（`0x1e01e20`）清除保存的累计量，没有独立 ACK。`05` 回包仍可能包含当前测试段的数据，因此回读电量、容量均为零才提示“累计数据已清零”；继续收到有效读数但累计未归零时只提示命令已发送。不会覆盖设备回读或自动补发。设备明确拒绝或读不到实时状态仍提示错误。

温度校准 `26` 的载荷为比例系数，不是摄氏度补偿量。原程序 `0x478f7c` 起将温度校准滑块下限 / 上限设置为 500 / 2000，`0x40df29` 将滑块值除以 `0x497ab4` 的 float32 常量 1000 后发送，因此应用在 UI 与协议层均限制为 **0.5–2.0**。默认显示四位小数，不附加 °C。

## USB 模式入口（2026-11-12 实机核准）

`MainDialog::buttonClicked`（`0x411960`）根据按钮文本选择命令，调用 `0x40e080`。该函数将参数放入报文偏移 3，偏移 4–7 清零，偏移 8–9 写 `EE FF`，然后经 `0x405150` 发送。完整模式命令为 `55 05 地址 命令 00 00 00 00 EE FF`，补零至 64 字节。

| 参数帧模式值（偏移 48） | 模式  | 命令 | 原程序调用 / 分支地址 |
| ----------------------- | ----- | ---- | --------------------- |
| 0                       | CC    | `47` | `0x411c0d`            |
| 1                       | CV    | `48` | `0x412384`            |
| 2                       | CR    | `49` | `0x4121c8`            |
| 3                       | CP    | `4A` | `0x4126a6`            |
| 4                       | IR    | `4B` | `0x41276c`            |
| 5                       | POWER | `4C` | `0x41285a`            |
| 6                       | CABLE | `4D` | `0x41290e`            |
| 7                       | CDC   | `4E` | `0x412b11`            |
| 8                       | CDCDC | `4F` | `0x412d18`            |
| 9                       | CDxn  | `50` | `0x412dca`            |

原函数还使用 `45 / 46 / 51` 进入其他设备页面，本轮未将其当作测试模式开放。没有使用猜测的 `30` 命令。

Windows 已在 BW150 V1.1.0、序列号 `924415` 实测以上 10 项，模式值逐项回读一致且始终停止。CC 目标为 `1 A`，CV / CR / CP 各自回读 `5 V / 5 Ω / 5 W`，恢复 CC 后仍为 `1 A`。IR / POWER / CABLE 的偏移 4 实测为 `00 00 00 03`，不能解释为普通浮点目标，保留未知字段；CDxn 的普通目标语义也未核准。

服务在发送模式命令或带 `expectedMode` 的参数 / 启动前，先查询并等待新的 `03` 和 `05` 报告；模式切换要求最新状态为停止。目标值与启动操作携带编辑 / 确认时的模式，回读模式不同则拒绝。模式命令只写一次，随后最多等待 2 秒，间隔 250 ms 重新查询；仅对应的参数帧模式值能确认成功，单独的成功 ACK 不算模式切换成功。失败不在界面提前高亮目标模式，也不重发切换命令。

2026-11-13 负载控件更新：目标、截止电压、过流 / 过功率保护、小时 / 分钟写入均先查询新参数与运行状态，再按当前模式检查应用限制；这几项必须回读对应 `03` 字段才能成功，单独 ACK 不计为设置完成。目标电流不超过过流保护且不超过 20 A；目标功率不超过过功率保护且不超过 400 W；CV 目标介于截止与 100 V；CR 目标介于 0.01 与 9999.99 Ω。反向修改保护 / 截止也必须维持关系。电流、功率、电压、电阻分别只接受 0.001 A、0.1 W、0.01 V、0.01 Ω 精度，比较设备边界时按此精度归一化 float32 回读。

时限仍为两条独立 `31` 命令，无新增组合报文。小时限制 0–99、分钟 0–59，组合范围 1–5999 分钟。一次界面应用仅写变化的字段：新小时为零时先写分钟，其余先写小时，避免正常跨小时调整时出现中间零时长；每条等待字段回读，中途失败停止并重新显示实际参数，不自动补发或回滚。这些上限来自当前 BW150 应用需求，不更改协议编码器原有适用于其它机型的宽范围定义。本次新增模拟传输层验证，未新增实机参数写入结论。

原始报文为 `artifacts/modes-raw-basic.json`、`artifacts/modes-raw-special.json`；原生界面验收为 `artifacts/windows-mode-switch.json`。进入特殊模式与完成特殊测试流程分别记录。

## 阶段提示与专用结果（2026-11-13）

原程序 `0x43b254` 起将 `05` 的偏移 54 拆成提示类型和选项；`0x405ab0` 起只在 CDC / CDCDC、状态非零、提示类型非零时打开 `CDPopTips`。`0x411630` 构造 `55 05 地址 35 动作 00 00 00 EE FF`；按钮、显示条件及字面文本已交叉核准，应用支持提示类型 2 / 3，其他提示不生成猜测的操作。后端要求最新模式、状态码和完整提示码与用户确认时一致，写入一次后等待提示解除；清除数据 / 继续动作还要求回读运行状态。此确认规则是新应用的保守实现，尚未用实机阶段写入验证。完整映射见 `special-tests.md`。

原程序启停槽 `0x41b620` 使用 `25 01 / 00`，未将专用模式排除。新应用为模式 4–8 提供确认启动，CDC / CDCDC 要求有效电池参数且没有待处理提示；CDxn 继续保留面板启动。未在实机执行专用启动、清除或阶段选择。

专用读数使用同一 `05` 帧的已核准字段，当前没有证据支持额外的专用结果帧。结果记录将运行中最后读数与停止时读数分开，不用停止后的 0 覆盖运行读数，不推定最终测得内阻、充放电阶段、完成原因或合格判定。

USB 升级的 App 操作见 [USB 固件更新](usb-update.md)。

## BW600 兼容协议

BW600 V2.0.3 和 V2.0.5 使用同一系列的 USB 控制帧。V2.0.5 的官方 PC 抓包确认产品名 `ATORCH BW600 V2.0.5`、`0483:5750`、`FF02 / 2` 和 64 字节 `03` / `05` 回复。历史抓包由 DL24 临时运行 BW600 固件取得，其中异常电流和温度仅用于核对字段布局。设备设置沿用原命令，USB 量程采用原厂手册列出的系列上限 200 V、50 A、1200 W，电流和功率目标仍受当前保护值限制。具体额定能力取决于设备功率模块。

- V2.0.5 固件将循环次数写入 `03` 的偏移 55（`0x1e02388–0x1e02396`）。`37` 命令从偏移 7 读取新次数（`0x1e0204e–0x1e02056`），面板范围 1–99。CDxn 的目标字段是放电电流，启动使用原有 `25` 命令，等待 `05` 确认运行。
- V2.0.3 的 `37` 分派指向默认返回，参数帧保留 `0x66` 占位。应用只在 BW600 回读有效次数时开放循环次数和 USB 启动。CDxn 阶段选择由设备面板处理。
- `BW600_BLE` 的广播名称由固件配置 `BW600_SPP` 派生。V2.0.5 的 GATT 表在 `0x1e61048` 起定义 FFE0 / FFE1，`0x1e0bd68` 起产生 36 字节旧版 DC 通知，`0x1e05caa` 起处理原有四键与三项清零。Wi-Fi 和经典蓝牙 SPP 使用各自的连接方式。

## BW150 蓝牙 BLE：独立的旧版直流协议

参考 APK 为用户提供的 `电能表.apk`，包名 `com.tang.etest.e_test`，版本 `1.0`，SHA-256 `9d93c1e7dc4f4d3a205f4b4bfeecf11b786244820dbf5ea9c2c7f6c23fa7ec61`。原文件未修改，也不纳入 Git；反编译结果位于忽略目录 `artifacts/vendor-ble/`。

静态分析 `Model/UUIDs`、`Model/BLEService` 和 `MainActivity.textValue`，再在用户授权的 Root 手机上被动记录原应用实际通知，确认：

- 设备名 `BW150_BLE`，本次地址 `00:00:00:17:BB:84`。
- 服务 `0000ffe0-0000-1000-8000-00805f9b34fb`，特征 `0000ffe1-0000-1000-8000-00805f9b34fb`，CCCD `00002902-0000-1000-8000-00805f9b34fb`。
- 本次 FFE1 属性为 `0x1c`（通知、写入、无回复写入）。应用订阅通知并使用有回复写入发送七条已核准的原生命令，详见 `bluetooth.md`。
- BW150 周期发送 `FF 55 01 02` 开头的 36 字节直流帧，约 1 Hz；本次分成 20 与 16 字节通知。Rust 解码支持任意分包与多帧合并，缓存有界，并在新头处重新同步。
- CCCD 订阅经回调成功后才完成连接；断开和连接失败会关闭 GATT。5 秒没有有效直流帧则标记失联，需手动重连。

实机帧：

```text
ff5501020000000000000002960000000000006400000000001a0001001c3c0000000023
```

| 偏移  | 类型                     | 本次处理                                               |
| ----- | ------------------------ | ------------------------------------------------------ |
| 0–3   | 固定头 `FF 55 01 02`     | 只接收旧版 DC 类型                                     |
| 4–6   | 大端 uint24 / 10         | 电压 V；原 APK 的 DC 分支换算规则                      |
| 7–9   | 大端 uint24 / 1000       | 电流 A；原 APK 的 DC 分支换算规则                      |
| 10–12 | 大端 uint24 × 10         | 容量 mAh；本次原始值 662，对应 6620 mAh，分辨率 10 mAh |
| 13–16 | 原 APK 作为累计 kWh 使用 | BW150 的该字段尚未与 USB 核准，当前不展示、不导出数值  |
| 24–25 | 大端 uint16              | MOS 温度 °C；捕获值 26 °C，传感器身份由用户确认        |
| 其余  | 状态、历史信息等         | 含义与校验算法未核实，不驱动控制或 UI 状态             |

功率采用电压 × 电流，未将帧中的其他字段解释为功率。2026-11-13 根据用户确认，将此前独立的 `deviceTemperature` 合并到 `mosTemperature`，与 USB 共用 MOS 温度通道；本轮未另做硬件温度对照。电阻、CPU / 探头温度、风扇、工作模式与负载启停状态仍未确认，缺失值使用 `null`。新版 CSV 仅写 `MOS_TEMP(℃)`，旧版 `DEVICE_TEMP(℃)` 列在导入时兼容归入 MOS；两列同时有值时保留明确的 MOS 值。电量没有用 0 或电压电流积分冒充设备累计值。

电压、电流的单位换算来自原 APK，当前实机验证在输入为 0、负载待机的条件完成；非零输入量程和负电流的含义仍待对照验证。尾字节的校验规则未确认，当前只校验类型与固定长度并做流同步，不宣称已验证 BLE 帧校验。

后续结合原 APK 和本台 V1.1.0 固件的 q32s 接收函数，核准七条 `FF 55 11 02 …` 原生命令：SET / OK / 加 / 减，以及分项电量 / 容量 / 计时清零。Windows / Android 已接入，四键经 USB 回读验证；清零未对实机执行。其余任意写入仍拒绝。原 APK 通用背光和电价不在 BW150 的处理分支内。FFE1 / FFE2 的 USB 参数读取探测仍只得到旧版通知，不提供 USB 隧道。完整包字节、固件地址、执行确认限制及前台服务见 `bluetooth.md`。

`tools/capture_ble.py` 默认只挂钩原 APK 的通知和写调用，保持原调用；显式 `--query-usb` 才进行上述只读查询探测。它需要 Root Frida 调试，仅用于还原协议。正式应用的 BLE 路径使用普通 Android 权限，不使用 Root / Frida，也不依赖原 APK。
