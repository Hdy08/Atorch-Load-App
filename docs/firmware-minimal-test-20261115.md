- 6 项故意损坏的内存样本均被离线校验器拒绝；没有将坏 CRC 或截断文件保存为测试固件，更没有发送给设备。

- 用户实测反馈：设备完全断电冷启动通过，标记存在，未发现功能异常，回刷原厂后完全恢复。

离线结构、CRC、重编码及差异核对通过；最小修改标记的运行、完全断电冷启动保持及回刷恢复得到用户实测反馈支持。没有新增逐包抓取、Flash 回读或独立参数 / 测量精度验收，不把用户观察报告为自动化实机验收或厂家验签通过。

## 无修改重建究竟验证了什么

工具使用 Python 标准库 `binascii.crc_hqx(data, 0)` 计算内部 CRC，单独实现 ENC / SFC 编解码以及目录结构的读取和序列化；然后与既有 `jl-misctools` 解包器的输出交叉核对。两个校验实现分别使用标准库与 `crcmod`。

重建包括：

1. 检查 Flash 头 CRC、顶层目录头、BANKCB 头及数据 CRC，解码配置中的 chipkey。
2. 解码完整有效应用区域，解析应用目录、文件和 P11 资源，验证非预留成员数据 CRC 和外层目录数据 CRC。
3. 重新填入提取文件，序列化各级目录、重新计算受影响 CRC，并重编码 BANKCB、顶层目录和 SFC 应用区域。
4. 保留原文件中的布局、间隙、预留条目、其他未解释字节和尾部填充，逐字节比较输出。

**这是针对固定原包、保留模板和原布局的无损重建工具。** 本轮没有重新压缩启动程序，没有尝试移动文件、改变成员长度或从零生成不同布局的通用升级包。BANKCB 的原压缩数据通过解码后重新编码，原数据字节得到完整保留；不把这一结果称为 LZ4 编码器或全型号打包器已验证。

## 修改点及引用关系

| 属性               | 值                                    |
| ------------------ | ------------------------------------- |
| 所属文件           | 解码后的 `app.bin`                    |
| APP 文件内偏移     | `0x54045`                             |
| 整包文件内偏移     | `0x58165`                             |
| 应用映射地址       | `0x01E54165`                          |
| 修改前，包含终止零 | `56 31 2E 31 2E 30 00`，即 `V1.1.0\0` |
| 修改后，包含终止零 | `54 31 2E 31 2E 30 00`，即 `T1.1.0\0` |

不能笼统地说整条原始版本字符串只被显示功能使用。本轮同时发现以下引用：

- `0x01E36ACA` 将完整字符串地址 `0x01E54165` 放入 `r8`。它与 `BW150`、`Model:`、`Version:`、`ID:` 等“关于”页内容相邻。
- 在两个界面分支中，`0x01E36B4A` / `0x01E371B0` 将 `r8` 放入文字参数 `r2`，随后 `0x01E36B4C` / `0x01E371B2` 调用 `0x01E089D4`。
- `0x01E089D4` 的已检查片段读取 `r2` 指向的字符，按字符值减 `0x20` 后索引字形表；后续逐位调用像素输出路径，直到零终止符。这支持完整字符串用于页面文字绘制。
- `0x01E0798C` 则读取从第二个字符开始的 `0x01E54166`，即 `1.1.0`。附近存在 `","v":"` 等 JSON 字段，支持其为信息构造路径的判断；本轮不修改这部分后缀。

因此选择只修改第一个字母。全 APP 的四字节字面量扫描和 `mov` 立即数模式扫描中，完整字符串起点只匹配到上述一次加载；后缀起点匹配到上述另一处加载，其余内部地址没有字面量匹配。这是有边界的引用检查，不能排除所有动态计算的指针。

USB 产品字符串是另一份独立的 UTF-16LE `ATORCH BW150 V1.1.0`，本轮确认其字节完整保留。**测试包即使成功运行，电脑中的 USB 产品名预计仍为原来的 V1.1.0；应在设备自身“关于”页观察 `T1.1.0`，不能只看电脑中的版本名。**

## CRC 变化及整包差异

内部文件 CRC 为多项式 `0x1021`、初值 `0`、不反射；与 USB 升级报文的 CRC16/Modbus 分开处理。

| 校验位置                              | 原值   | 修改后 |
| ------------------------------------- | ------ | ------ |
| `app.bin` 数据 CRC，内层目录 `0x4022` | `26BD` | `B668` |
| `app.bin` 目录头 CRC，`0x4020`        | `743C` | `1339` |
| `app_area_head` 数据 CRC，`0x4002`    | `C640` | `395F` |
| `app_area_head` 目录头 CRC，`0x4000`  | `8AF5` | `3BF7` |

上表是解码后的数值。下面才是最终升级文件中的原始字节差异，数值因 SFC 编码而不同：

| 整包偏移  | 原字节 | 新字节 | 用途           |
| --------- | ------ | ------ | -------------- |
| `0x4000`  | `F2`   | `F0`   | 外层头 CRC     |
| `0x4001`  | `A5`   | `14`   | 外层头 CRC     |
| `0x4002`  | `1E`   | `01`   | 外层数据 CRC   |
| `0x4003`  | `7A`   | `85`   | 外层数据 CRC   |
| `0x4020`  | `33`   | `36`   | APP 条目头 CRC |
| `0x4021`  | `4B`   | `2C`   | APP 条目头 CRC |
| `0x4022`  | `C3`   | `16`   | APP 数据 CRC   |
| `0x4023`  | `DA`   | `4A`   | APP 数据 CRC   |
| `0x58165` | `EC`   | `EE`   | 字符 `V` → `T` |

除此之外没有整包字节差异。特别核对了：

- `[0, 0x4000)` 与原包逐字节相同，包含 Flash 头、顶层目录、包内启动程序及配置。
- APP 长度、入口 `0x01E00120`、应用区域基址 `0x4000`、chipkey `0x8D07` 均相同。
- `app.bin` 除这一显示字符外逐字节相同；其他四个提取成员完全相同。
- 有效载荷结束于 `0x9C326`；后面的 3,290 字节仍为原样 `FF`。
- VM、PRCT、BTIF、USERIF 和 key_mac 的目录元数据保留。包内没有的实机预留区内容仍未读取，不把“目录未变”称为实机参数区已经备份或具有写保护。

## 校验器的损坏样本检查

所有损坏样本只在内存中构造，使用正常编码生成对应字节后交给离线解析器；没有向设备发送。

| 情况                                 | 实际拒绝原因                     |
| ------------------------------------ | -------------------------------- |
| 改坏 Flash 头 CRC                    | `Flash header CRC`               |
| 改坏顶层条目头                       | `Directory header CRC at 0x20`   |
| 改坏 APP 条目头                      | `Directory header CRC at 0x4020` |
| APP 数据改变但未更新 CRC             | `Inner data CRC: app.bin`        |
| 外层数据 CRC 错误，但目录头 CRC 正确 | `Outer data CRC: app_area_head`  |
| 截断到 160 字节                      | `Truncated BANKCB`               |

另外，重复构建产生同一输出；逆向还原显示字符后重新打包，得到原厂文件的完整相同字节。第三方解包交叉检查覆盖原包、无修改重建包和测试包各五个文件，以及各自完整解码容器。

这些检查验证本机工具能识别已列出的错误，不代表设备面对坏文件会返回相同错误，也不代表原厂认证机制已经被测试。

## 复现方式

本机已有 Python 及 `.local/jl-python`、`.local/jl-misctools`、`.local/q32-python`、`.local/ghidra-jieli` 依赖。工具固定检查四个关键解析及指令定义文件的摘要；没有下载、安装或修改依赖。

在仓库根目录，用一个尚不存在的输出目录运行：

```powershell
& 'C:\Users\Administrator\AppData\Local\Python\bin\python.exe' -B tools/firmware_minimal_test.py --output artifacts/firmware-minimal-test-20261115-reproduce
```

省略 `--output` 时只在内存中完成相同检查并输出 JSON，不写测试文件。指定目录已存在时直接拒绝，不覆盖原件或既有实验记录。脚本不包含设备通信或启动官方程序的入口。

本轮工具 SHA-256 为 `6df237d285d68eba85b3c2c9c2d069bc753a33af84f0feff11d37c29883b52ae`；完整 `analysis.json` 为 `6d1a1f5ecf50e4faa53925f58702c96d75a4c1d75f41ec110a832c11431791ea`，`manifest.json` 为 `d3862fd853920ea685e6b532822bd364e591f0635e0be3a96026974ab2e59906`。独立复核已重新读取清单内全部 9 个文件，大小及摘要均一致。
